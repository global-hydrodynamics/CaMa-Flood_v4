# CaMa-Flood v5 Tutorial Development Plan

## Status and scope

This document describes the staged tutorial framework. Tutorial 02 now has a researcher-approved specification, four implemented experiment scripts, completed 2000–2003 simulations, analysis scripts, and reference figures on `feature/gosh-refactor`. The beginner-facing README and any package assembly changes remain separate follow-up work.

The framework is intended to become the primary beginner-oriented entry point for v5 experiments when its materials are implemented and validated. Existing `gosh_sample/` workflows remain available as implementation references; this plan does not remove or reorganize them.

## Three distinct documents and artifacts

### Experiment specification

An experiment-specific specification describes the scientific objective and learning outcomes, domain and datasets, simulation period and numerical settings, physical configurations, scientific comparisons, expected outputs, and questions requiring source inspection or validation. It should describe what experiment is intended and why, not become a command-by-command tutorial.

The initial specification may be drafted through researcher–AI discussion and can contain incorrect or incomplete assumptions. Before implementation, a coding agent must inspect relevant Fortran source, namelist definitions, input data, and existing scripts. The agent should produce a technically grounded English specification, identify discrepancies, and bring unresolved scientific decisions to the researcher. It must not silently turn uncertain assumptions into confirmed settings.

### Common tutorial authoring guide

A reusable guide defines the README structure, writing style, evidence requirements, and verification steps shared by Tutorial 01, Tutorial 02, and later tutorials. It is separate from each experiment specification so the same authoring method can be reused without making the scientific plans interchangeable.

### Generated tutorial

The tutorial is the human-facing account of an implemented and validated experiment. It connects the scientific goal to the actual settings, commands, files, observed results, and interpretation. It is not generated by merely paraphrasing the specification: it must reflect the source, scripts, data contracts, and execution evidence.

## Planned workflow

1. **Researcher–AI experiment design:** Discuss the scientific objective and prepare a provisional experiment-specification draft.
2. **AI source and data investigation:** Inspect model code, namelists, datasets, and existing workflows to establish technical facts and constraints.
3. **Interactive scientific review:** Present confirmed facts, incompatibilities, feasible configurations, and unresolved scientific choices to the researcher. The researcher makes the scientific decisions, with further discussion as needed.
4. **Specification revision and approval:** Incorporate those decisions into the version-controlled specification. Repeat investigation and review until the researcher approves a scientifically meaningful and technically feasible design. Source-code investigation alone is not design approval.
5. **Experiment implementation:** Develop scripts and in-scope support tools from the approved specification under a separately approved task.
6. **Execution and scientific verification:** Run the experiments, check technical behavior, and produce comparisons from actual outputs. Record commands, environment, and observations; the researcher reviews important scientific interpretations.
7. **Tutorial generation:** Use the approved specification, validated implementation, execution evidence, and common authoring guide to write the human-facing tutorial.
8. **Final consistency review:** Check the scientific objectives, specification, scripts, data, outputs, figures, tutorial, and package contents together.

Execution results may expose technical or scientific issues and return the work to interactive review and specification revision. The specification is an evolving design record, not a one-pass translation into settings. An AI must not finalize a scientific design solely because it has found a technically valid configuration.

Experiment design, implementation and validation, and tutorial writing are separate stages. Findings from source inspection may revise the specification before implementation. A tutorial may describe only operations and results that were actually checked.

## Tutorial documentation and evidence

Tutorials should support researchers who are new to the workflow and are not expected to know Fortran internals. Explain what each major operation accomplishes and why, which settings and files matter, the command to run, what files or output to expect, how to recognize operational success, and how to interpret results scientifically.

Use copyable terminal commands and representative stdout/stderr captured from real runs. Do not use screenshots of terminal windows. Long output may be shortened only when the omission is stated and the remaining excerpt preserves its meaning. Figures and reference results must be generated from actual model output and labeled with the conditions that produced them. Never invent expected numerical results or describe an untested operation as verified.

As appropriate to an experiment, guide users through inspecting the tutorial and input directories, reading key GOSH settings, running the default case, checking outputs and logs, copying and editing an experiment script, running variants, and inspecting or visualizing results.

The tutorial README should explain the reproducible workflow without duplicating detailed source-code documentation. Experiment-specific scientific rationale belongs in its specification and interpretation section; common authoring requirements belong in the shared guide.

## Tutorial 02: four-experiment specification

Tutorial 02 specifies a 2000–2003 Mekong simulation with annual Restart handoffs, NetCDF runoff/output/Restart, and four configurations: Default, No Bifurcation, Kinematic Wave, and No Floodplain. Four GRDC locations and one MRC-referenced Can Tho model location are used only for simulation-output sampling. The four-year execution, daily hydrograph comparisons, and annual-maximum spatial figures have been generated and checked; no observed discharge comparison is made. The current specification, evidence, and remaining scientific questions are in [`tutorial/tutorial02-mekong_netcdf_4exp/experiment_spec.md`](../tutorial/tutorial02-mekong_netcdf_4exp/experiment_spec.md). The beginner-facing README and package integration remain future work.

## Repository and beginner-package policy

The GitHub repository is for development and should retain the complete validated experiment implementation. Tutorial 02 now has `mek_default.sh`, `mek_nobif.sh`, `mek_kine.sh`, `mek_nofld.sh`, its experiment specification, visualization tools, and verified reference figures. The beginner README is still pending. Generated simulation outputs, Restart files, and run logs are not to be tracked.

The downloadable beginner package has a different teaching purpose. Its planned Tutorial 02 contents include the tutorial documentation, visualization tools, verified reference figures, and only `mek_default.sh`. Users will practice creating the No Bifurcation, Kinematic Wave, and No Floodplain scripts by copying and editing the Default configuration. Those three scripts remain in GitHub and are excluded during package assembly, rather than deleted from the repository. Packaging behavior has not been implemented by this plan.

## Tutorial 01 implementation and manual-authoring experiment

Tutorial 01 is implemented under [`proj_sample/tutorial01-get_started/`](../proj_sample/tutorial01-get_started/). Its manual documents a clean build and a 40-day Mekong run using bundled inputs, with results isolated under the tutorial's `out/` directory. The workflow was executed in a disposable checkout of `feature/gosh-refactor` on macOS Apple Silicon; the reset script was also run after the simulation and preserved `config/Mkinclude`. This is operational validation of the development branch, not validation of a separately assembled release package or scientific correctness.

The first manual-authoring experiment and its assessment are recorded in the Tutorial 01 directory. The original manual-writing guidelines and experiment design are retained there unchanged for comparison. The run succeeded with system Python because its CTL scripts use the standard library; installation of the full optional Python requirements was blocked by package-index DNS access in the test environment. Tutorial 02's beginner-facing README and package integration remain separate follow-up work.

## Long-term goals

- **Human learning:** help students and researchers design, run, debug, and interpret simulations.
- **AI-assisted development:** provide agents with structured scientific context and explicit questions rather than relying only on unstructured source and README files.
- **Reproducibility:** connect scientific objectives, configuration, commands, outputs, and verification evidence.
- **Maintainability:** make tutorial updates traceable when source, data formats, or workflows change, with revalidation on regeneration.
- **Reusable knowledge:** accumulate reviewed experiment specifications, validated workflows, and scientific explanations for future work.

These are goals of the proposed framework, not demonstrated outcomes.
