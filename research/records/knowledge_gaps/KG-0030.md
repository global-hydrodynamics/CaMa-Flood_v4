# KG-0030: Acceptability of Float32 visualization copies for Float64 Restarts

- Gap ID: `KG-0030`
- Linked event ID(s): `EV-0330`
- Category: visualization interface / data precision
- Evidence basis: GrADS descriptor documentation and local executable dependency inspection
- Status: open

## What remains unclear?

Standard GrADS gridded Binary descriptors read 32-bit floating-point records. CaMa-Flood's default Binary Restart uses Float64. The new helper creates a separate Float32 visualization copy and points the CTL at it. The original Restart is untouched, but the visualization values are rounded to Float32. Confirm whether this default behavior is acceptable for the intended user workflow or whether users should instead receive an error unless they explicitly request a down-converted view.

## Discovery trigger and why it matters

The Phase B requirement asked for GrADS CTLs for both Float32 and Float64 Binary Restarts. The GrADS variable-format documentation describes standard gridded Binary records as floating-point data and the local OpenGrADS install could not be started because its `libgrib2c.0.dylib` dependency is missing. A CTL has no documented standard Binary Float64 selector. The implementation therefore preserves the source and creates an explicitly named Float32 preview copy rather than writing a CTL that would interpret 8-byte values as 4-byte values.

The choice affects convenience, disk use, and display precision, but does not modify model Restart data or model calculations.

## Verified facts

- The model writes Float64 Binary Restart records when `LRESTDBL=.TRUE.` and Float32 records when false.
- The local GrADS launcher reports a missing `libgrib2c.0.dylib`; actual GrADS reading was unavailable in this environment.
- The generator converts only a newly created preview copy and directs the CTL to that copy; it never overwrites the Restart file.
- Synthetic checks verified Float64-to-Float32 record conversion, expected order, and output size.

## Maintainer review needed

Confirm the user-facing policy for Float64 visualization: retain the current automatic, clearly reported Float32 preview, or require an explicit conversion flag / decline CTL generation for Float64 files. The current implementation is safe for source preservation but is lossy for display values.

## Verification and limits

The temporary Float64 fixture converted to a Float32 copy with the same record order and expected file size. Live GrADS reading could not be tested because of the missing dynamic library. The down-conversion is not appropriate for restart input or scientific numerical analysis.

## Why the gap matters

Visualization can tolerate some loss of precision, but the application should make it clear when a user is viewing rounded values. The preview copy is explicitly named and the full-precision source remains available; the default trade-off still needs maintainer confirmation.
