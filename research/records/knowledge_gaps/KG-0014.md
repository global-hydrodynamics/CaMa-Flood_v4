# KG-0014: High-resolution area selection and tiled-map support

- Gap ID: KG-0014
- Linked event IDs: EV-0179, EV-0193, EV-0196, EV-0197, EV-0201, EV-0202, EV-0203, EV-0204, EV-0205, EV-0206
- Category: architecture / map data contract
- Evidence basis: legacy and v5 source inspection, v4.30 package files and metadata, AllocRiverGauge manual, and maintainer explanation
- Status: resolved_for_phase

## What was initially unknown?

Phase A left open whether v5 allocation programs had to support multiple high-resolution areas. Phase B approved a single selected area and rejection of multi-area layouts. The source established the behavior, but the scientific and historical reason for applying that limit to allocation had not been recorded. Later review also found that the same limit must not be generalized to workflows that aggregate pixels across areas.

## How was it discovered?

During Phase B allocation migration, `map/tools/code/mod_allocation_map_io.F90:read_allocation_hires` was found to require `narea == 1`; the regression test checks that a two-area location file is rejected. The Mekong sample itself has one area. The Phase B completion record described the single-area boundary but did not distinguish allocation's river-network search from pixel-aggregation workflows.

## Verified facts

- The shared v5 allocation reader rejects any `location.txt` area count other than one. Flow-gauge, dam, and level-gauge allocators use this reader. The regression covers rejection of a multi-area layout.
- The inspected v4.30 package has one global 1-minute area (`map/glb_15min/1min/location.txt`, 21600 x 10800) and one Japan 15-second area (`map/tej_01min/15sec/location.txt`, 6000 x 5280; 123–148 E, 24–46 N). The Japan directory contains 11 binary layers, 10 CTLs, and `location.txt` (about 1.11 GB total). The AllocRiverGauge manual describes distinct first-stage maps at 30 arcsec global and 5 arcsec Japan. The maintainer confirms these are allocation-specific maps and are distinct from the 1-minute and 15-second layers distributed with CaMa-Flood.
- Legacy and v5 parameter input-matrix programs iterate through the `narea` rows in `location.txt` and accumulate pixel-to-grid contributions. The v5 regional default matrix generator does the same.
- Legacy `map/src/src_param/calc_prmwat.F90` and v5 `map/tools/code/param_water_calc_prmwat.F90` iterate through listed areas and aggregate selected pixel areas by base-map catchment.
- `region_combine_hires.F90` iterates over listed areas when processing regional high-resolution layers.
- Existing focused tests do not establish package-scale multi-area correctness. The committed Mekong sample is one area; the permanent-water synthetic fixture is also one area.

## Maintainer-confirmed rationale

The upstream AllocRiverGauge process first allocates and reviews station/reservoir records on a high-resolution river network. The maintainer explained that this stage addresses reported location and drainage-area problems and discrepancies between MERIT Hydro and real-world drainage areas. CaMa-Flood's river network derives from MERIT Hydro, so the corrected high-resolution locations and catchment areas are expected to correspond internally with CaMa-Flood's unit catchments. The AllocRiverGauge manual documents the two-stage workflow and QA/QC; the extra consistency rationale is maintainer-provided and is not proof that each record is accurate.

The allocation stage therefore needs correspondence to a sufficiently accurate river topology and catchment network, including network traversal for level gauges. It does not need the finest available floodplain inundation-topography grid just because that grid is finer. The maintainer identifies one globally continuous 1-minute area and one Japan 15-second area, both distributed in the CaMa-Flood package, as the intended CaMa-Flood allocation inputs. The AllocRiverGauge v1.2 manual's global 30-second and Japan 5-second maps are separate first-stage allocation inputs. Their distinct workflow roles resolve the apparent resolution mismatch; no derivation relationship between the grids is claimed.

## Resolution trace

1. **Question: Why was single-area processing selected for allocation?** Resolved by maintainer explanation plus source and manual review. The one-area rule preserves traversal over one selected high-resolution river network for a second-stage map correspondence operation. Resolution formalized in `docs/map_data_tools_plan.md` and linked from the allocation workflow documentation.
2. **Question: Must future v5 allocation support multiple areas?** This is a scope decision, not an unresolved defect. The maintainer states that multi-area allocation is not a required follow-up for the initial v5 migration. Reconsider only if a separately approved use case requires it; no implementation is authorized by this record.
3. **Related but distinct capability:** matrix generation, regional matrix generation, permanent-water aggregation, and regional high-resolution combination process multiple areas. Their source-level loops are preserved and documented. This does not constitute large-package validation.

## Verification boundary and remaining follow-up

The multi-area aggregation behavior is established by source inspection, not by a multi-tile integration test. The inspected global 1-minute and Japan 15-second package directories each declare a single area; no multi-area package dataset was verified in this task. A maintainer-operated procedure is documented in `docs/map_data_tools_plan.md`; execution remains pending until an available dataset declares multiple areas. This is a validation-coverage item, not a scientific knowledge gap and not evidence that the source capability is unsupported.

The distinction between the manual's allocation-specific 30/5-arcsec maps and the package's CaMa-Flood 1-minute/15-second layers is resolved by maintainer clarification and package inspection. It does not prove row-level allocation accuracy. The package's inspected global 1-minute and Japan 15-second `location.txt` files each declare one area; they do not exercise multi-area processing. The multi-area integration check remains pending only for a package dataset that actually declares multiple areas.
