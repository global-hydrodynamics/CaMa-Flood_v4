# KG-0025: Binary initial-output call and output record numbering

- Gap ID: `KG-0025`
- Linked event ID(s): `EV-0275`, `EV-0276`, `EV-0277`
- Category: output file contract / workflow
- Evidence basis: source-code evidence
- Status: partially verified

## What was unknown or assumed?

When `LOUTINI` is enabled with binary output, does the initial-output call write a binary record, and can that call affect the record numbering of later output? This matters because the new CTL tool derives record count and time coordinates from the binary file size.

## How was it discovered?

While implementing the `existing` mode, source review traced the `IRECOUT` counter and initial-output branch in `src_main/cmf_ctrl_output_mod.F90`. The question was recorded before the implementation guard was added. The behavior concerns output records, not numerical calculations.

## Verified facts

- `CMF_OUTPUT_WRITE` increments `IRECOUT` before selecting data and writing output (`src_main/cmf_ctrl_output_mod.F90`, line 486).
- When `KSTEP == 0` and `LOUTINI` are true, the routine cycles past the writer for binary mode because initial storage output is limited to NetCDF (`src_main/cmf_ctrl_output_mod.F90`, lines 593-596).
- By source control flow, the next scheduled binary write therefore uses the next record number after the skipped initial call. A runtime file-layout reproduction was not performed here, so the exact bytes allocated for an unwritten direct-access record remain unverified.
- The model's default `LOUTINI` is false. The current Mekong sample does not set it true.

## How was the knowledge formalized?

`tools/generate_output_ctl.py` rejects binary CTL generation when `LOUTINI=.TRUE.` rather than assuming a record layout. `tools/README.md` documents the reason. The Fortran behavior was not modified.

## Resolution trace

- Resolution method: source analysis; no runtime reproduction
- Evidence or maintainer explanation: `CMF_OUTPUT_WRITE` increments `IRECOUT` at line 486, then skips binary writing in the `KSTEP==0` and `LOUTINI` branch at lines 593-596.
- Final interpretation and rationale: binary output with `LOUTINI=.TRUE.` is not safe for inferred CTL record counting until the skipped-record behavior is runtime-tested or the source contract is changed. The tool fails closed for this configuration.
- Formalization location(s): `tools/generate_output_ctl.py`; `tools/README.md`; VR-0086
- Human review: pending

## Verification and limits

The synthetic validation confirmed that the tool rejects the configuration. It did not run the model with `LOUTINI=.TRUE.` and therefore did not establish the exact direct-access file size or whether all supported compilers materialize an unwritten record slot identically.

## Why the gap matters

An incorrect assumption about an initial record would shift every subsequent CTL timestamp or produce a false record count. A future maintainer may separately decide whether to fix the Fortran output counter or preserve the existing behavior; that decision is outside this task.
