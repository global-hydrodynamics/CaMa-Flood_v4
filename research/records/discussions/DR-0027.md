# DR-0027: Separate MPI partitioning from region coloring

- Discussion ID: `DR-0027`
- Linked event IDs: `EV-0153`, `EV-0154`
- Source type: Maintainer task instruction
- Source reference: Maintainer-provided task attachment in the active Codex task; no transcript copied
- Source access: restricted
- Maintainer review: pending

## Question and context

MPI region assignment (`mpireg-N.bin`) and display-color generation had been coupled. That made a visualization product look like a side effect of partition creation and limited independent coloring of partitions with other process counts.

## Evidence examined

- `map/tools/code/param_mpi_set_region.F90` and `param_mpi_set_basin.F90`
- `map/tools/code/param_bif_set_basin.F90`, including its `set_color` routine
- Legacy reference `map/src/src_param/set_bif_basin_mpi.F90:set_color`
- s04, the shared Makefile, registry-driven CTL generation, and MPI tests

The coloring routine uses class size, neighboring assigned colors, map-edge wraparound for global grids, and a fixed display palette. The existing v5 implementation also has a fallback to color 10 when the palette is exhausted. The standalone utility can operate from `mpireg-N.bin` plus map geometry in `params.txt`; it does not need basin aggregation inputs.

## Alternatives discussed

- Keep coloring inside region partitioning: rejected because it couples display postprocessing to computation partitioning and prevents manual postprocessing as a separate operation.
- Map region IDs directly to palette indexes: rejected because that discards the established size- and adjacency-aware coloring behavior.

## Proposal (not yet a decision)

Use a shared coloring module so the basin-color and MPI-region-color paths do not maintain duplicate algorithms. Make coloring a standalone analysis executable.

## Maintainer decision and rationale

The task instruction approves separate partitioning and coloring programs, no `mpireg.bin` alias, numbered `mpireg-N.bin` products, automatic coloring and bifurcation-connectivity analysis only for the configured default count, and manual color generation for other counts. The existing visually tuned coloring approach is to be retained. This is a responsibility/interface refactor; basin aggregation and region-assignment algorithms are to remain unchanged.

## Implementation instruction, if any

The user-provided task attachment is the implementation instruction. Its requested scope excludes `map/src/`, the main `src/` tree, and `gosh/`.

## Outcome or unresolved questions

Implementation centralizes coloring in `map_color_mod`, used by both the basin-color program and `analysis_mpi_region_color`. The MPI utility colors the region IDs in its input, whereas the earlier basin-color product colored basin groups; therefore equal numeric colors or byte-for-byte equality with the old basin-group visualization is not a valid compatibility criterion. Tests verify region-color structure, output layout, naming, and use of the shared registry metadata. This does not establish scientific validity of the MPI partition or visual quality for all maps.
