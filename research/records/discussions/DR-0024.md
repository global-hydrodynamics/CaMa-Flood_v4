## Question and context

The v5 MPI basin aggregation program had no optional map showing how its basin groups changed the original basin connectivity. The existing standalone analysis has a different purpose: it evaluates whether bifurcation pathways are represented for a selected MPI partition.

## Evidence examined

- Legacy calculations and classifications in `map/src/src_param/set_bif_basin_mpi.F90`.
- Current aggregation flow and parsed bifurcation pathways in `map/tools/code/param_set_bif_basin_mpi.F90`.
- s04 message/cleanup behavior and the shared registry-driven CTL generator.
- Temporary-copy comparisons and tests recorded in `VR-0049`.

## Alternatives discussed

No alternatives were recorded in the task instruction. It specified restoring the legacy classification calculations into one optional two-record diagnostic and keeping partition-specific connectivity analysis separate.

## Proposal (not yet a decision)

None. The task instruction supplied the accepted implementation contract.

## Maintainer decision and rationale

The maintainer-approved task scope is to accept `check_map` in the MPI basin aggregation call and optionally write `check_bif_bsnmod_mpi.bin`. Record 1 is `bifmod_mpi`; record 2 is `bpoint_mpi`. The product is computed after MPI basin aggregation and before assignment to MPI regions. Its classifications may depend on `normal` versus `MaxMPI` thresholds, but not on the later partition count. Without `check_map`, the output must not be created or overwritten. The diagnostic is not a model runtime input.

Keep `analysis_check_mpi_bifurcation` as the separate partition-dependent analysis of `mpireg-N.bin`. Do not restore the old separate MPI diagnostic files in the v5 workflow, alter legacy `map/src/`, or change the basin-merging algorithm.

## Implementation instruction, if any

The task authorizes a focused v5 change to the MPI aggregation program, s04 wrappers, registry, CTL/documentation, and validation. The completed implementation retains the legacy classification rules: `bifmod_mpi` uses classes 0/1/2; `bpoint_mpi` uses classes 1/2/3 and the maximum class when pathways share a cell. Both use `-9999` for not-applicable cells.

## Outcome or unresolved questions

The feature and documentation were implemented, with the optional diagnostic compared record-by-record against the legacy program on temporary Mekong sample copies. The generated CTL was checked through `s06-write_ctl.sh`. These checks establish implementation compatibility for the inspected sample and fixtures, not scientific validation of basin aggregation or a full MPI model run. The review summary remains pending maintainer review.
