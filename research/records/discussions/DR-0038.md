## Context

Phase A documented the v4 allocation tools and planned a parity-preserving migration. Phase B authorized the implementation on `feature/map-data-tools` and required incremental work, preserved v4 sources, regression evidence, documentation, and research logging.

## Approved implementation boundaries

- Preserve `map/src/src_param/` programs and legacy wrappers unchanged.
- Place shared map-input code and three distinct `allocate_*` programs in `map/tools/code/`; put wrappers in the existing `map/tools/script_params/` family.
- Keep scientific matching, thresholds, category decisions, and output formats unchanged.
- Require an explicit `HIRES_TAG`; support exactly one high-resolution area and reject multi-area layouts.
- Use the approved `map/data/MLIT_LevelGauge_allocated.csv` in the new v5 level-gauge workflow; do not rewrite the legacy v4 wrapper.
- Preserve fixed-width text products, including a persistent dam error output.

These boundaries come from the maintainer's task instructions, not from an inference that all future allocation workflows must use this exact interface.

## Implementation and validation evidence

The v4 outputs were captured with GNU Fortran 14.2.0 and saved under `map/tools/tests/data/allocation/legacy_gfortran_14_2/`. The test compiles preserved v4 and new v5 sources in temporary directories, checks source hashes and saved snapshots, compares numeric text to printed precision, and verifies single/multi, dam categories, level types, explicit high-resolution selection, multi-area rejection, and sample-map non-mutation.

The initial dam port omitted the legacy conversion of positive `ctmare` values from m² to km². Regression output placed the ordinary river category into the small category. The conversion was restored in the v5 copy; the legacy source was not changed. The final regression passed for all six output files.

Shared input I/O resides in `map/tools/code/mod_allocation_map_io.F90`. Matching, upstream ordering, and path traversal remain in their corresponding programs. New scripts and docs are linked from `map/tools/script_params/README.md`; the milestone plan is `docs/map_allocation_migration_plan.md`. The completed work was committed as `ef9fec9b9fef249821cdcf049ae5d69a59410e58`, pushed to `origin/feature/map-data-tools` over SSH, and reported in Issue #122.

## Knowledge-gap review and remaining limitations

The Phase B milestone review checked scientific thresholds and classifications, input/output contracts, historical rationale, cross-document consistency, and implementation assumptions. No additional material gap was introduced by the migration. Existing questions remain linked rather than duplicated: the rationale for legacy allocation thresholds (`KG-0012`) remains open; row-level provenance for Mekong additions in `GRanD_alloc+Mekong.csv` remains incomplete (`KG-0013`); multi-area high-resolution support is explicitly outside this phase (`KG-0014`); and the historical origin of the old v4 MLIT filename remains undocumented although the v5 input is approved (`KG-0015`). These do not block parity-preserving migration. The tests establish software compatibility for selected Mekong records and synthetic cases in this compiler environment, not independent scientific accuracy.
