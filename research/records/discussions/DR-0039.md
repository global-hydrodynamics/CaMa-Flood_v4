# DR-0039: High-resolution area contracts across map workflows

- Discussion ID: `DR-0039`
- Linked event ID(s): `EV-0201`–`EV-0206`
- Source type: Maintainer task clarification and repository evidence

## Context

The Phase B allocation migration selected one high-resolution area and tested rejection of multi-area layouts. A later task clarified that high-resolution area counts must be treated according to the scientific operation: allocation maps externally prepared river-network locations to CaMa-Flood catchments, while several other workflows aggregate local pixels across areas.

## Maintainer-provided rationale and constraints

The upstream AllocRiverGauge tool already places and reviews external stations/reservoirs on MERIT Hydro before CaMa-Flood's second-stage mapping. The maintainer explained that the first stage addresses reported location and drainage-area discrepancies and that shared MERIT-derived river topology is expected to provide internal correspondence. Allocation consequently prioritizes river topology and catchment mapping, not the finest floodplain terrain resolution. The maintainer identifies the distributed global 1-minute and Japan 15-second CaMa-Flood areas as the allocation inputs. The AllocRiverGauge v1.2 manual (updated 2024-11-22) describes separate first-stage global MERIT Hydro and Japan J-FlwDir maps at 30 and 5 arcsec, respectively. The package confirms one global `1min` area and one `tej_01min/15sec` area. These configuration statements are not proof of universal adequacy or individual allocation accuracy. The initial discussion's uncertainty about the differing resolutions was resolved in follow-up `DR-0040`.

The one-area allocation rule remains an intentional v5 contract for flow gauges, dams, and level gauges. Multiple-area allocation is not a required task for the initial v5 migration. This does not restrict established multi-area pixel aggregation in input-matrix or permanent-water workflows.

## Repository evidence

- `map/tools/code/mod_allocation_map_io.F90:read_allocation_hires` rejects `narea /= 1` and loads one area's layers.
- `map/tools/tests/test_allocation_regression.py` checks that a two-area allocation input is rejected.
- The inspected v4.30 package's `map/glb_15min/1min/location.txt` contains one global 1-minute area, and `map/tej_01min/15sec/location.txt` contains one 15-second area over Japan. The upstream v1.2 manual describes the separate first-stage J-FlwDir map at 5 arcsec.
- Legacy and v5 input-matrix programs loop over area rows; legacy/v5 permanent-water programs also loop over area rows; `region_combine_hires` processes multiple source areas.
- Current small GitHub fixtures do not establish large-package multi-area integration behavior.

## Documentation and implementation outcome

A single technical section in `docs/map_data_tools_plan.md` now records the cross-workflow contract, evidence level, and a maintainer-operated multi-area validation procedure. Concise links were added to allocation, parameter, regional, and map-tools documentation. Source comments were added to the v5 shared allocation reader and per-area aggregation loops; no executable behavior was changed.

The map-variable registry was also extended for the five current v5 allocation text products (`GRDC_alloc.txt`, `GRanD_error.txt`, `GRanD_river.txt`, `GRanD_small.txt`, and `MLIT_levelgauge.txt`). Existing `workflow_stage` values were preserved.

## Open evidence limits

The apparent resolution mismatch was later clarified: the manual's global 30-second and Japan 5-second maps are allocation-specific first-stage maps, while the distributed CaMa-Flood package provides global 1-minute and Japan 15-second layers. See follow-up `DR-0040` and `KG-0014`. Full-package multi-area integration for input-matrix, permanent-water, and regional-combination workflows remains pending for any dataset that actually declares multiple areas; source loops alone are not test evidence. No scientific validation is claimed.
