## Question and context

How should new CaMa-Flood v5 workflow scripts balance readability with input and failure handling? A prior s04 MPI wrapper had accumulated checks and bookkeeping that made the processing sequence difficult to understand. The maintainer requested a general, permanent convention, alongside simplification of the parameter workflow scripts.

## Evidence examined

- Existing s01-s04 parameter scripts and their map-local Mekong copies.
- Shared Fortran executables under `map/tools/code/` and their argument/work-directory expectations.
- Existing wrapper tests, including tests that asserted shell-level missing-input rejection.

## Alternatives discussed

- Keep wrappers as defensive application layers with preflight checks and extensive bookkeeping.
- Treat scripts as readable sequences of researcher-style terminal commands, reserving wrappers for configuration, order, working directory, and simple orchestration.

## Proposal (not yet a decision)

The second approach was proposed as the general style, with checks moved to the input-consuming program where validation is necessary.

## Maintainer decision and rationale

The maintainer approved the second approach as a community recommendation (not mandatory and not retroactive) and as the default for AI agents in the current maintainer-led v5 modernization. The intended scripts should be human-readable command sequences rather than defensive frameworks. Keep configuration near the top, prefer direct calls, do not auto-build or routinely check standard map inputs/executables, and avoid duplicated validation and bookkeeping. Preserve simple CLI handling and safe temporary cleanup; readability must not undermine scientific correctness, reproducibility, or cleanup.

The maintainer additionally approved common STEP/SUCCESS/ERROR output patterns for s01-s04, implemented directly in each script with no shared helper. Errors must identify the script, current step, and original nonzero status. Preserve `set -eu`, POSIX shell behavior, failure propagation, and s04's temporary-file cleanup; default connectivity analysis must complete before SUCCESS. The purpose is to make failures unmistakable after verbose Fortran logs.

The policy applies to future v5 scripts under `script_region/`, `script_params/`, and `script_analysis/` as an AI-agent default, while remaining a recommendation for community contributors. It does not authorize unrelated numerical, interface, backward-compatibility, or legacy `gosh/` changes.

## Implementation instruction, if any

Simplify s01-s04 and the Mekong sample copies; standardize self-contained messages and test success/failure paths; update the authoritative agent rules, AI workflow guide, map-tools and parameter-workflow guides; record the approved convention. Keep numerical algorithms, parameters, binary formats, and legacy `gosh/` scripts unchanged.

## Outcome or unresolved questions

The scripts and documentation were updated, one consumer-program `BIFLAYER` guard was added, and wrapper regression expectations were updated to confirm that missing required paths reach the compiled programs. In follow-up, the maintainer requested executable-path variables use an `EXEC_` prefix, comments identify the actual calculation, and temporary map rasters remain visible rather than hidden because they can approach gigabyte scale. The MPI temporary raster was renamed consistently in the wrapper, Fortran programs, tests, and guide; cleanup behavior is retained. Self-contained STEP/SUCCESS/ERROR messages and simulated failure tests were added. The maintainer then asked that the message trap block follow the user-editable settings, keeping the start of each script focused on configuration; the same exit behavior and cleanup remain. The discussion summary remains pending maintainer review. Some compiled map tools have incomplete input diagnostics; these are known implementation gaps to consider separately, not a reason to restore duplicated wrapper prechecks.
