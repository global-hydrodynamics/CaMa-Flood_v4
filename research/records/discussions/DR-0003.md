## Scope and chronology reconstructed from evidence

The maintainer authorized an independent v5 regional workflow under `map/tools/`, preserving legacy v4 regional sources, and initially excluded CTL generation and data execution from the implementation task (EV-0020). The maintainer later clarified that CTL generation was separated as a staged scope choice, not because of a technical dependency (EV-0068). The implementation added five regional Fortran programs, a script template, shared build machinery, and READMEs (EV-0021). The work was committed with the existing documentation/metadata at `ad7d544` on 2026-10-30. Later commits `c2b1aac` and `ea14d6b` refined map registry, workflow guidance, tests and CI; they are not evidence that the full regionalization algorithm was scientifically validated.

The build design passed through three recorded placements. EV-0023/24 specify a unified Makefile, `region_`/`param_` naming and a map-specific build output. EV-0026/27 move executables into each map-local `script_region/`. EV-0029/30 establish explicit builds into shared `map/tools/code/`, with map-local workflows calling those shared executables while retaining their current directory for relative data paths. The final arrangement is documented in source and templates. The maintainer later confirmed that v4/v5 separation protects current v4 users and permits backward-compatible parallel development, that the shared build directory was chosen for readability, and that CTL generation was separated as a staged scope choice.

## Decisions and implementation facts

- The v5 regional workflow is a parallel source tree; this task's scope explicitly kept legacy v4 sources unchanged.
- Five current regional Fortran source files were copied into `map/tools/code/`; VR-0005 reports byte comparisons with `map/src/src_region/`.
- The final build uses explicit Makefile targets and one shared executable location. Map-local scripts do not compile the tools and must be run with their map-local directory as the working directory.
- CTL generation was deferred as a deliberate scope-sequencing choice and handled as a separate phase (EV-0068). The original B1 implementation/build checks did not execute the map workflow; a later maintainer-run Mekong generation is documented in HI-0002.

These are evidence-backed decisions and behaviors. No additional rationale is inferred here.

## Maintainer clarifications received after the reconstruction

- The five v5 regional sources were kept separate from the v4 directories because users still depend on the GitHub v4 repository. Replacing active directories with v5 changes could disrupt those users; parallel development also needs backward-compatible improvements to remain possible while contributions from other users continue.
- The shared `map/tools/code/` location was selected as a developer preference: keeping related code and executables together makes the layout easier to see and understand.
- The maintainer reports that developers commonly run manual experiments to check code behavior, and confirmed personally running this v5 Mekong workflow. The exact source revision/build, shell command line, and checks beyond generation were not recorded.

These are maintainer-confirmed rationales/context, not claims that the layout was selected through a formal comparative evaluation. The maintainer also set the regionalization phase completion boundary at generation of the Mekong regionalized dataset; this does not assert independent scientific validation (EV-0069).
